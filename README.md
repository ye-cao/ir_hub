# IR Hub

Home Assistant 红外遥控集成，内置 **irext 码库**。

它自己不含硬件，只负责"查码 + 发码"：把码库里的时序交给 HA 的红外发射器
（如 ESPHome `ir_rf_proxy`）发出去。

```text
IR Hub 实体 ─ infrared.async_send_command ─ infrared.<emitter> 实体
  ─ aioesphomeapi ─ ESPHome ir_rf_proxy ─ remote_transmitter ─ IR LED
```

## 能做什么

| | 码库 | 生成的实体 |
|---|---|---|
| 电视 / 机顶盒 / 风扇 / 音响… | 按键码库：**13,615 设备 / 1,818 品牌 / 258,653 键** | 每设备 1 个 `remote.*`，每键 1 个 `button.*` |
| ⭐ 空调 | 状态码库：**245 品牌 / 1,507 型号**（索引引用 509 个 bin） | 每型号 1 个 `climate.*` 恒温器面板 |

空调是真恒温器：模式 / 温度 / 风速原生可调，重启自动恢复状态，不需要 SmartIR / SmartAC。

## 两种添加方式

添加集成时二选一：

| 方式 | 怎么用 | 适合 |
|---|---|---|
| **手动选择** | 大类 → 品牌 → 型号 | 知道型号，或想指定具体型号 |
| **用遥控器配对** | 拿原遥控器对准红外接收器按一下，自动在码库反查 | 不知道型号；机顶盒这类同款 OEM 遥控有几百个的情况 |

配对方式需要 HA 的红外**接收**能力（见「依赖」）。按键类设备按**任意一个键**即可；
空调按遥控器的**电源键**（同一个 bin 能生成的帧很多，实测按一个键就够定位型号）。

## 依赖

| 项 | 要求 |
|---|---|
| Home Assistant | **≥ 2026.6.0**（`InfraredEmitterConsumerEntity` 在此版本引入） |
| 红外发射器 | 四选一，见下表 |
| 红外接收器 | **仅"用遥控器配对"需要**。HA 的红外接收实体比发射支持更晚引入；版本不够时集成会直接提示，不会报错 |

**发射通道**（添加时选）：

| 通道 | 目标 | 说明 |
|---|---|---|
| `infrared`（推荐） | infrared emitter 实体 | HA 官方红外体系，配 ESPHome `ir_rf_proxy` |
| `broadlink` | `remote.*` 实体 | 现成遥控宝；打包格式与 SmartAC 逐字节一致 |
| `esphome` | `esphome.<动作>` | SmartAC 兼容契约（`{"command": [带符号时序]}`） |
| `mqtt` | topic | 默认发 SmartAC 裸时序数组；选项里可切 Tasmota IRMQTTServer RAW JSON |

ESPHome 侧最小配置（仅 `infrared` 通道需要）：

```yaml
remote_transmitter:
  id: ir_tx
  pin: GPIO4
  carrier_duty_percent: 50%     # 必须是中间值，0/100 会被拒
  non_blocking: true

infrared:
  - platform: ir_rf_proxy
    name: IR Transmitter        # ⇒ HA 里出现 infrared 发射器实体
    remote_transmitter_id: ir_tx
```

## 安装

### 方式一：HACS（推荐）

1. HA 里先装好 [HACS](https://hacs.xyz)（设置 → 设备与服务 → HACS，首次需授权 GitHub）。
2. 添加本仓库，二选一：
   - 点链接直达（需已配置 My Home Assistant）：
     [HACS 添加 ir_hub](https://my.home-assistant.io/redirect/hacs_repository/?owner=ye-cao&repository=ir_hub&category=integration)
   - 或手动：**HACS → 右下角「自定义存储库」** → 仓库填 `ye-cao/ir_hub`、类别选 **Integration** → 添加 → 下载。
3. 重启 Home Assistant。
4. 设置 → 设备与服务 → 添加集成 → 搜 **IR Hub**。

> 有新版本时 HACS 页面会提示，点更新 + 重启即可。

### 方式二：离线安装

1. 下载仓库（Code → Download ZIP，或 `git clone https://github.com/ye-cao/ir_hub.git`）。
2. 把 `custom_components/ir_hub/` **整个目录**拷到 HA 的 `config/custom_components/ir_hub/`
   （拷完应存在 `config/custom_components/ir_hub/manifest.json`）。
3. 重启 Home Assistant → 添加集成 → 搜 **IR Hub**。

> HA 跑在容器/虚拟机里时，注意拷进**容器内**的 `/config`（Samba 或 File editor 插件均可）。

## 添加流程都带实测确认

不管手动还是配对，**最后都会真发一帧码让你确认设备有反应**才建 entry —— 避免"加错了删掉重来"。

- 按键类设备：发 `power` 键。没反应可以「自动试下一个型号」（机顶盒这类多型号品牌不用逐个回下拉重选，试完全部自动停），人不在设备旁可跳过。
- 空调：**两段式**，先发开机帧再发关机帧。只发关机码的话，空调本来就关着，看不出任何反应。
  配对找出来的型号也走这一步；没反应退回候选列表换一个（不用重新按遥控器）。

## 用法

**空调**：得到 `climate.*` 后用恒温器卡片。每次调温度/模式/风速会发一帧全状态码
（美的类协议自动连发 3 帧）。两次操作间隔 ≥ 1 秒。

**电视 / 机顶盒**：每个可用键已生成 button，dashboard 点一下即发：

```yaml
type: grid
columns: 4
square: true
cards:
  - type: button
    entity: button.tcldian_shi_1_power
    name: 电源
  - type: button
    entity: button.tcldian_shi_1_vol_plus
  - type: button
    entity: button.tcldian_shi_1_vol_minus
```

或者只用 remote 实体调服务（可一次多个键）：

```yaml
service: remote.send_command
target: {entity_id: remote.tcldian_shi_1}
data:
  command: ["vol+", "vol+"]     # 键名取自实体的 activity_list 属性
```

调试逃生口 —— 绕过码库直接发裸时序：

```yaml
service: ir_hub.send_raw
data:
  emitter: infrared.<你的发射器实体>
  timings: "3963 -3985 491 -1990"   # 也接受列表；正 = 载波，负 = 空闲，单位 µs
  carrier: 38000
  repeats: 1
```

### 空调面板只显示这台空调真有的选项

码库里每台空调的能力是**逐模式**不同的（实测 525 个 `.bin`：**353 个**至少有一个模式
没有温度维度、**338 个**各模式的风速集合不一样）。老版本把全模式的**并集**丢给面板，
面板于是给出库里根本不存在的组合，一点就报
`不支持组合 模式=fan_only / 风速=auto / 温度=30°C` —— 用户看到的就是"按了不执行"。

现在面板按**当前模式**声明能力：

| 分量 | 声明方式 | 例子（美的 11837） |
|---|---|---|
| 温度 | 该模式没有温度维度时**整个不显示滑条** | `fan_only` 无温度；`cool` = 17~30°C |
| 风速 | 只列该模式真有的档位 | `cool` 4 档；`auto` / `dry` 只有自动风 |
| 摆风 | 库码里有摆风才出现 | 见下一节 |

自动化 / 脚本 / 语音里塞进不支持的组合也不会再失败 —— 集成会把不支持的分量**就近替换**
成同模式下可用的值并照常发码（例如往 `auto` 模式塞 `high` 风 ⇒ 实际发自动风；塞 35°C ⇒
实际发 30°C）。想看某台空调到底支持什么，直接读实体的属性：

- `ir_hub_fans_by_mode` —— 每个模式可用的风速
- `ir_hub_temps_by_mode` —— 每个模式的温度范围（空列表 = 该模式没有温度维度）
- `ir_hub_swing_modes` —— 摆风档位（缺省 = 这台不走摆风）

> 门禁：`tools/selfcheck.py` 穷举 525 个型号 × 91936 种组合（模式 × 风速 × 边界温度 ×
> 每种摆风档）调 `frame_for`，断言**永远给出非空时序** —— 有任何一个组合取不到帧就算失败。

### 摆风

摆风在库里有两种完全不同的形态，集成按证据强弱分别处理（实测 525 个 bin：
状态帧 **332** / 独立功能帧 **83** / 无 **110**）：

| 形态 | 库里长什么样 | 面板表现 |
|---|---|---|
| **状态帧维度**（332） | 摆风是状态帧里的一位，改档位只让帧内 1~2 个元素变化 | 出现「摆风模式」下拉，档位取自库里的档位表 |
| **独立功能帧**（83） | 库里没有摆风段，但遥控器上有**独立的摆风键**（`FUNCTION` 键 6） | 出现「摆风模式」下拉：`关` = 默认帧、`开` = 在帧上叠上那个功能键。**用户的美的 11837 属于这一类** |
| 无（110） | 两者都没有 | 面板**不出现**摆风项 |

两个必须知道的限制：

- **`开` / `关` 这两个标签是推断的**。库码只声明了"这一位 / 这一键存在"，没声明它语义上是
  "扫风开关"还是"风向档位"。两档以上时面板用中性名 `1` / `2` / …（下标即档位），
  不编造"上下 / 左右"。**按一下看风叶怎么动，就能确定哪个标签对应什么**，再看要不要改名。
- **空壳段会被丢掉**。375 个有摆风段的 bin 里，43 个**各档位生成的帧完全相同**（段是空壳，
  拿来当摆风会出现"点了没反应"）⇒ 不当作摆风：其中 15 个退回独立功能帧、28 个判为无摆风。

### 实体命名

中文设备名会被 slugify 成拼音：`TCL电视-1` → `remote.tcldian_shi_1`。
拿不准就去「开发者工具 → 状态」按前缀筛，别照中文猜。

`+` / `-` 在 entity_id 里映射为 `plus` / `minus`（裸 slugify 会把 `vol+`、`vol-` 都压成 `vol` 而撞名）；
显示名仍保留原始 `vol+`。同见 `page+/-`、`brightness+/-`。

## 选项与排障

| 选项 | 默认 | 说明 |
|---|---|---|
| 载波频率 (Hz) | 38000 | **别信码库里的协议名** —— 本机 TCL 电视标"RCA (56K)"，实测却是 38 kHz 才响。设备没反应就换 38000 / 40000 / 56000 试 |
| 发送次数 | 1 | HA 的 esphome emitter 会丢弃 `repeat_count`，所以在时序层复制实现 |
| Broadlink 延迟 | 0.5 秒 | 仅 Broadlink 通道有效（`remote.send_command` 的 `delay_secs`） |
| MQTT 载荷格式 | smartac | 仅 MQTT 通道有效 |
| 发射通道 + 目标 | 添加时选的 | **可以直接换**（infrared / Broadlink / ESPHome / MQTT）—— 不用删了重加集成，更不用重新配对；保存后条目自动重载 |
| 室温 / 湿度传感器（可选） | 空 | 只用于恒温器卡片**显示**室温湿度（红外单向拿不到回读） |
| 功率传感器（可选） | 空 | 接空调的智能插座：ON/OFF 用来同步「物理遥控器开了 / 关了空调」（只看开关，不看瓦数） |

### 温湿度与功率传感器（可选）

红外是单向的，空调状态本来只能"显示最后发送的状态"。配了外部传感器后可以补上两块：

- **室温 / 湿度**：在选项里填传感器实体 id（留空不用），值原样显示在恒温器卡片上。
- **功率**：接空调的智能插座。插座 ON 且面板当前是关机 ⇒ 面板同步成**开机**状态
  （回到上次开的模式），**不发红外**；插座 OFF ⇒ 面板同步成关机。
  判断口径与 SmartAC 一致：只看 ON/OFF，不看瓦数阈值。
- 配了功率传感器后，"用物理遥控器开机 → HA 面板跟着亮"这条链路就通了 ——
  这也是判断"红外码有没有真的发出去"的土办法之一。

设备没反应时的排查顺序：① 选项里换载波 → ② 换同品牌其它型号 → ③ 检查发射强度
（直驱 LED 建议加三极管，ESP32 可把 `drive_strength` 拉到 40mA）。

### 配对方式能用多快

按键类设备的代价主要在**建该大类的特征索引**（第一次用才建，之后常驻内存）：

| 大类 | 首次识别 | 同进程再识别 |
|---|---|---|
| 机顶盒（最大类） | ~9 秒 | ~1 秒 |
| 电视机 | ~6 秒 | ~2 秒 |
| 风扇 / 音响 / 投影仪 / DVD | < 1 秒 | < 0.3 秒 |

按两个键比只按一个键更准：两个键的候选取交集，能把同款 OEM 遥控（码库里几十上百个同码型号）收敛掉大半。
第二键可以跳过。

空调走另一套路子（详见下节）：先按**结构指纹**（帧长 + 引导码）把 509 个 bin 筛到 30 个上下再逐帧打分。
指纹建一次约 0.5 秒，之后单次识别均值 1.2~1.6 秒（最慢 5 秒出头，机器空闲时更快）。同样支持第二键取交集。

### 空调是怎么配对的

按键设备"一键 = 一帧定长码"，直接比就行。空调不是：一个 `.bin` 描述的是一台机器**整套**
编码规则，帧要按 `[模式][风速][温度]` 现场生成，全库枚举出来有十几万帧。

所以配时分两级：

1. **结构指纹预筛** —— 每个 bin 只生成 1 帧，取 `(帧长, 首个 mark)`。同一台空调的所有状态帧
   这两项恒定（全库 509 bin 实测**零例外**），所以拿捕获帧比一下就能筛掉九成（实测 509 → 中位 27）。
2. **逐帧打分** —— 只对留下的 bin 把帧一帧帧生成出来比（每台最多 301 帧），按相似度排序。

结果就是**型号列表**（不是键列表）。同一协议族的近似型号会一起冒出来（它们的码只差几个 bit），
所以：**按品牌挑一个，集成会先发开机帧、再发关机帧让你确认**；没反应退回列表换一个
（配对路径的「自动试下一个」就是"下一个匹配候选"，不用重新按遥控器）。

> 码库里大量型号是**多品牌共用**的通用码（509 个 bin 里 149 个，最多的一个被 216 个品牌共用）。
> 从 bin 反查不出"你这台是什么牌子"，所以配对出来的候选会标成「空调 11272（79 个品牌共用）」，
> entry 名也只叫「空调 11272」—— 不挑一个品牌来冒充。
> 手动选择路径的品牌是你自己点的，照旧写成「美的 空调 11272」。

> 实测（`tools/verify_learn_ac.py`，120 个真实 bin 注入 ±8% 接收抖动 + 10% 丢首元素）：
> 真型号在候选前 8 里 **120/120 = 100%**，排名第 1 的 85.8%；两键取交集仍 100% 留住真型号；
> 结构指纹零误杀、结构不变式零违反。

### 配不上时怎么判断卡在哪一环

配对失败本来只有一个笼统症状 ——「按了没反应」。所以每一环都做成**可以自己看**的：

| 你看到的现象 | 真实含义 | 怎么办 |
|---|---|---|
| 「状态」一直是 `unknown`，按遥控器也不变 | 帧**根本没进 HA**：接收器选成了别的设备，或那台设备离线 | 接收器下拉现在带**设备名**（如 `HJY IR 红外接收（infrared.xx_ir_receiver）`）—— 选你正对着的那台。`unknown` 就是「这台接收器从未收到过任何一帧」 |
| 提交后报「没能订阅到接收器」 | 订阅就没成功（实体被删 / 不是红外接收实体） | 回上一步换一个接收器；具体原因会一并写在表单顶部 |
| 提交后报「接收器实体不存在 / 设备离线」 | 下拉里那个名字已失效 | 同上 |
| 明明写着「已收到 0 帧」，却照样列出了候选 | **正常，不是乱选** —— 那个数字是**打开页面那一刻**的快照（你先看页面、后按遥控器，所以它几乎总是 0） | 匹配页会列出**真正用于匹配的帧**（几段 / 首脉冲 / 全长），以它为准 |
| 提交后报「没捕获到红外信号」，但「状态」明明是个**时间戳** | **单看一个时间戳证明不了什么** —— 它是"**历史上**最近一次收到帧的时刻"，可能是几分钟前那次成功的测试 | 提交失败时会做**打开本页那一刻 vs 此刻**的前后对比，直接告诉你断在哪一环（下一张表） |

提交失败时，表单里会直接给出诊断，把笼统的「没信号」拆成互不相干的三类：

| 诊断 | 真实含义 | 怎么办 |
|---|---|---|
| ❗ 帧根本没进 HA（回调 0 次 + 状态没变） | 红外**没打到这颗接收头**上：选错接收器 / 没对准 / 距离太远 / 设备离线 | 确认对准下拉里选中的那台；在 ESPHome 日志搜 `remote.pronto` 或 `remote.raw`，**日志里没有就是信号没进来**，与码库无关 |
| ⚠️ 帧进了 HA，但回调一次都没被调用 | 接收器状态**已前进** ⇒ 那台设备确实收到了信号，断在订阅上 | 原样再按一次重试；仍如此，把这一行连同上一次按键的时刻一起发出来 |
| ⚠️ 信号进来了，但一帧都没能规整出来 | 帧到了，但**不可用**。会列出原因（含 0 / 太短 / 非数字）**和原始时序前 24 段** | **不是码库的问题**，是接收侧把波形记坏了 —— 见〈接收端记录质量〉 |

> 这三类的**处置完全相反**（前两类去修"信号怎么进来"，第三类去修"进来的波形质量"），
> 所以不能混成一句"没信号"。账本还会把每次丢弃的原因分类计数，日志里同时留原始片段，
> 便于直接拿波形做反向复现。

匹配页还会给结果一句判词（连续相似度口径：库里真值 ≥0.90，同协议族近似 ≈0.85）：

- **≥0.85 可信** —— 第一个候选基本就是它。
- **0.75 ~ 0.85 偏低** —— 可能是同族近似型号，发实测码试一下最直接。
- **<0.75 太低** —— 列出来的只是最近邻，**不是匹配结果**。
  选列表最后的「↩ 退回重按」重新配对（**务必按第 2 键**），或用「手动选择码库」按品牌找。

> 实测对照（两支遥控，同一条链路）：库里真值 → 最高 **0.945**、召回 **20 个**候选；
> 库里没有的（300 段 NEC 系）→ **只有 1 个**候选、最高 **0.67**。
> 而"300 段"这一档在 509 个 bin 里**总共只有 1 个**，所以「只有 1 个候选」本身就是
> 「库里没有这只遥控」的信号，而不是"选中了很准"。**候选数多才是好迹象。**

**空调多一层判别**：低分可能是「库里没有这只遥控」，也可能是「捕获被记坏了」—— 两者解法相反。
所以空调的判词会额外报一个**结构预筛幸存数**（只问"这一帧的**形状**——帧长 ±3 段 + 引导码——
库里有没有对应"）：

- 幸存数 **≤3** ⇒ 形状都对不上，**基本断定不在码库里**，重配对救不回来 → 走「手动选择码库」。
- 幸存数**正常（十几~几十）而候选寥寥** ⇒ 形状对、细节错，多半是**捕获被记坏了** → 重按一次
  （按得干脆、离接收器近些），仍不行就换 ESP32 做接收端。

### 遥控器连发被接收端「粘成一帧」

空调遥控器的电源键发的是**完整状态帧**（模式 / 风速 / 温度 / 摆风一起发），而且通常会**连发好几遍**。
接收端 `remote_receiver` 是按**静默**切帧的（`Signal is done after 10000 us`，默认 10 ms），
连发之间的间隔小于 10 ms ⇒ 这几遍被**粘成一整帧**。于是同一次按键，可能捕成 200 段、也可能 300 段，
而码库里存的是固定遍数，帧长对不上就会被预筛整库灭掉，**症状和"这只遥控不在码库里"一模一样**。

所以匹配引擎多了一趟容错：在捕获的内部长 gap（≤ −3000 µs）处把帧**截断出几个前缀**再比一遍。
实测（2026-09-30，同一台空调的真实捕获）：

| 捕获 | 结构预筛幸存 | 最高分 | 判词 |
|---|---|---|---|
| 300 段原样 | 2 | 0.632 | ❌「不在码库」——**错的** |
| 截到 200 段 | 27 | **0.866** | ★ 命中真型号 |

把库帧和捕获都按 100 段一块切开逐位比，两个 burst 块与库内 `('on','cool','auto',26)` / `('off',)`
**逐位完全相同** —— 遥控确实在库里。

> 代价做了控制：截断只在**第一趟没找到像样候选**（最高分 < 0.85）时才启用。因为带前缀会让一批
> "长度只有一半"的库帧也过预筛（空调幸存 bin 27 → 59、单次匹配 1.5 s → 2.7 s）。
> 0.85 这个线是实测卡的：120 例空调抽样里 **119 例第一趟就 ≥0.85**（重跑率 ≈1%），
> 而**错帧的上界只有 0.765** ⇒ 门槛必须高于 0.80 才能拦住"碰巧同长的错帧"冒充结果。

### 接收端记录质量：ESP8266 的上限在哪

接收端是**软件计时**还是硬件解码，直接决定"长帧能不能记全"：

| | ESP8266（如 HJY-WF-YK100 / ESP-12F） | ESP32 |
|---|---|---|
| 解码方式 | 软件 ISR 计时（`remote_receiver.cpp`） | RMT 硬件（`remote_receiver_rmt.cpp`） |
| `buffer_size` 默认 | **1000 个脉冲**，**不会自动扩容** | 10000，且会扩到"需要的两倍" |

> 实测本库全部帧长（`tools/measure_frame_lengths.py`）：空调最长 **596 段**（p99 531、中位 180）；
> 按键类 258,653 个键里最长 **500 段**（中位 72）。**全部 < 1000** ⇒ 对"库里存在的码"来说，
> ESP8266 的默认缓冲**够用，不是瓶颈**，不必去调 `buffer_size`。

两个真正要注意的点：

- **`dump: all` 是纯开销**：它让 **36 个协议解码器**对**每一帧**全跑一遍。而 ir_hub 的红外通道
  拿的是**原始时序**（`infrared` 平台直接转发 `get_raw_data()`），**不依赖 `dump`**。
  ESP8266 上要留日志看原始时序，用 `dump: raw` 就够；不用了就去掉 `dump:`。
- **截断的唯一硬证据**：ESPHome 日志里出现 `[W][remote_receiver] Buffer overflow`。
  出现它才说明真的溢出了（即"要发的码比库里最长的还长"，或主循环被长时间阻塞）。
  没出现就别往这个方向找。

## 码库说明

**两个来源**合成一份按键库：

- **collect**（8,565 设备）：用户上传的采集码，中文名。
- **decode**（5,050 设备）：官方解码库，即官网 code 页的"控制码"，英文名。
  设备 id = 索引 id + 100000。

按官网基准 1:1 入库（remote_index 每行独立成条，不做签名去重 —— 否则品牌下型号数与官网对不上；
重复条目信号逐值相同，gzip 只多 0.4 MB）。存储 4.7 MB，按 16 个类别分块，运行时只解压用到的那一块。

**空调**用的是另一套状态码库（`ac_library/`，索引引用 509 个 bin），解码器移植自
[SmartAC](https://github.com/ryanh7/SmartAC)（irext 官方 `ir_decode.c` 的 Python 移植，MIT）。

> 两份都只存**无符号长度**，符号在读取时按"偶 mark / 奇 space"补。漏了这步会得到全正数组，
> 被 `RawTimingsCommand` 直接拒收，一次都发不出去。

## 自检

开发机直跑，不依赖 HA，约 1.5 分钟：

```bash
python tools/selfcheck.py
```

**296 项**，覆盖：

- 全库每个键的 varint **逐字节往返**（用打包器自己的编解码重编比对，不抽样）
- 符号交替不变式（保证发得出去）
- 空调全库 525 个 bin 文件（索引引用 509 个）全量解码回归
- `remote` / `button` / `climate` / `config_flow` 的真逻辑单测（stub 掉 homeassistant）
- 翻译键与 config_flow 用到的键一一对应（含 `_learn_capture_error` 会返回的三个 error 键）
- 学习匹配引擎的不变式（符号规整、丢引导码对齐、分数不饱和）
- 空调配对全链路（选空调大类 → 捕获电源键 → 候选列表 → 两段式实测 → 退回候选 → 建 entry）
- 配不上的**可诊断性**：0 帧拆成三种病因（订阅失败 / 接收器实体不存在 / 真没信号）、
  匹配页摊开真实用到的帧并给出可信度判词、低分时「退回重按」有出口
- **回调侧账本**：首次打开不挂判词（用户还没按，挂出来必然误报）、
  「状态没变 = 帧没进 HA」与「状态变了但回调 0 次 = 断在订阅」分别报出、
  丢帧原因（含 0 / 太短 / 非数字）四类互不混淆且分类计数、保留原始样本
- **空调结构预筛幸存数**：低分时区分「不在码库里」（幸存 ≈1）与「捕获被记坏」（幸存正常）
- **接收端把重复发送粘成一帧时的容错**：`burst_prefixes` 能在内部长 gap 处截出原始帧、
  合并过的捕获照样排第 1（按键类）/ 照样命中真型号（空调）
- **按模式的能力表自洽**：全库每个 bin 的 `fans_by_mode` / `temps_by_mode` / `swing_modes`
  与实际 `commands` 的层数、键数逐项核对（面板就是照这张表声明的）
- **「无所不能」门禁**：525 个型号 × 91936 种组合（模式 × 风速 × 边界温度 × 每种摆风档）
  一律能取到非空时序 —— 钉死"按了不执行"
- **climate 动态能力**：切模式后风速/温度/摆风跟着变、越界值收敛到最近可用值、
  `fan_only` 不声明温度特征、无摆风的型号不声明摆风特征
- **选项流（发射通道 + 传感器）**：目标下拉按通道出、旧 emitter 失效仍能打开表单
  （提交时给明确报错）、换通道重画且保留已填值、传感器字段随 entry 保存
- **可选传感器**：温湿度只显示不伪造、无历史状态也挂订阅、功率 ON/OFF 同步开/关机
  且不发红外、同状态事件忽略、没配传感器零订阅

末尾有 `expected_total` 项数护栏：**任何一段检查被静默跳过都会报错**，所以"全部通过"这个结论本身可信。

## 已知边界

- **红外是单向的**：没有状态回读。`remote` 的 state 恒为 unknown；`climate` 的状态是"最后发送的状态"，
  用物理遥控器操作不会同步进来。
- 码库只覆盖 irext 收录的设备。没有的可以用 `ir_hub.send_raw` 手发时序。
- emitter 掉线会自动跟随（一起 unavailable，上线自愈），不需要重加集成。
- 配对方式只对**同一个大类内**做反查：先选大类（按键类某个类别，或「空调」），再按遥控器。
  空调的候选是"型号"，同一个协议族常有几十个近似型号一起出现 —— 按品牌挑一个，再靠两段式实测确认；
  多品牌共用的通用码会标出共用品牌数。
